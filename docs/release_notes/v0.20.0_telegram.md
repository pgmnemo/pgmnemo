**pgmnemo 0.20.0** — «Граф, который достаёт»

Два новых механизма расширения кандидатного пула в `recall_hybrid`. Оба по умолчанию выключены — если вы не трогаете GUC, поведение побайтово совпадает с 0.19.1.

**Что добавлено.**

Вариант A — BFS по каузальным рёбрам (`graph_expand_weight`, дефолт 0.0). Из топ-K ANN-якорей делается обход графа в ширину глубиной 1 только по рёбрам с `edge_kind='causal'`. Уроки, которые достижимы по графу, но не попали в исходный ANN+BM25 пул, добавляются в кандидаты. Хаб-кэп обязателен: в реальных данных p99 исходящей степени = 222, без ограничения поиск превращается в лавину. По умолчанию `graph_expand_per_node = 10`.

Вариант C — GIN-поиск по entity keys (`graph_entity_expand_weight`, дефолт 0.0). Для каждого ключа из `entity_keys` запроса делается LATERAL-скан по GIN-индексу через `metadata @> jsonb_build_object('entity_keys', jsonb_build_array(key))`. Уроки, совпадающие по сущностям, но не попавшие в пул, добавляются в кандидаты.

Новый столбец `retrieval_source TEXT` (18-й) в выдаче `recall_hybrid`: `'ann'`, `'graph'` или `'entity'` — откуда пришёл урок. `stats()` теперь возвращает 7 дополнительных столбцов с текущими значениями GUC.

**Чего в релизе нет — и почему это важно.** Никаких заявлений о том, что граф улучшает качество поиска. Такие числа появятся после завершения предзарегистрированной аблации PREREG_020_EXPAND (SHA 4eb3a2b8). Код отделён от заявлений о качестве — публикуем механику сейчас, числа — после честного эксперимента.

**Совместимость.** Если вы обращаетесь к `recall_hybrid` по позиции столбцов — добавьте 18-й столбец в свой тип строки. Именованный доступ и `SELECT *` не затронуты. Пустой `mem_edge` → поведение идентично чистому гибриду, без деградации.

Обновление: `ALTER EXTENSION pgmnemo UPDATE TO '0.20.0'`. Пути с 0.17.0, 0.18.0, 0.18.1, 0.19.0 и 0.19.1 проверены — обновлённая установка побайтово совпадает со свежей (G-UPGRADE-PARITY).
